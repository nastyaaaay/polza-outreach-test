# Polza Agency — тестовое задание "Вайбкодер-аутричер"

Пайплайн: сбор базы B2B-компаний, персонализация, сборка цепочки писем и
проверка базы клиента (Задачи 1-4).

## Что делает

Ниша: IT/маркетинговые агентства, Россия (Москва).

Ниша выбрана намеренно: агентства сами понимают, зачем им лидогенерация через холодный аутрич — это не случайная выборка компаний.

### Пайплайн (два прохода, честно про почему)

**Проход 1 — `collect_leads.py`.** Для каждой компании из `companies_seed.py` (61 название, собраны вручную через 2ГИС — категории "маркетинговое агентство", "digital агентство", "SMM агентство", "SEO агентство"):

1. Ищет официальный сайт через DuckDuckGo HTML-выдачу.
2. Скачивает главную страницу и, если нужно, страницы "Контакты"/"О компании" и "Команда" — вытаскивает email и имя контактного лица.
3. Забирает реальный текст о компании (meta description + первые содержательные абзацы) и отдаёт его локальной LLM (Ollama, `gpt-oss:20b` — тот же сервер, что в проекте [smart-intake-automation](https://github.com/nastyaaaay/smart-intake-automation)) с инструкцией сформулировать 1-2 предложения персонализации **строго на основе реального текста**, без выдумывания фактов.
4. Пишет результат построчно в `output/leads.csv` — прогресс не теряется при сбое на середине долгого прогона.

После ~10 успешных компаний DuckDuckGo (а следом и Bing, и Google) начали отдавать капчу/anomaly-страницу вместо результатов — обычная защита от автоматических запросов, не баг в коде. Ждать неопределённое время разблокировки было нерационально, поэтому источник поиска сайта пришлось сменить.

**Проход 2 — `pass2.py` + `known_domains.py`.** Для компаний, чей сайт не нашёлся из-за блокировки, домен находился через карточки организаций в 2ГИС (открытый бизнес-справочник, отдаёт реальный сайт компании в разделе контактов) — вручную для части списка, остальное можно повторить тем же способом. `known_domains.py` — просто словарь "компания → найденный домен", `pass2.py` берёт его и прогоняет ту же логику fetch → email → LLM-персонализация, что и в проходе 1, без повторного поиска.

**`finalize.py`** — сборка `output/leads_final.csv`: убирает компании без сайта и компании, чей "сайт" на самом деле оказался соцсетью/каталогом (не сайт — значит нет данных, не подставляем выдумку), дедуплицирует, чистит служебные суффиксы в названиях (добавлялись только для точности поиска), санитизирует текст персонализации (markdown, юникод-мусор, утёкшие суффиксы) и один найденный мусорный email (случайный технический адрес аналитики ВКонтакте на групповой странице, не контакт компании).

**`build_emails.py`** — мёржит `output/leads_final.csv` с шаблоном `email_sequence.md` (Задача 3) в готовые к отправке письма: подставляет имя и персонализацию с честными фолбэками там, где их нет, вместо того чтобы ломать текст письма или врать. Заодно следит за лимитом ТЗ (до 120 слов на письмо) — если персонализация не влезает, укорачивается она, а не выверенный текст письма. Подробности — в самом `email_sequence.md`.

**`export_for_sheets.py`** — разворачивает результаты в CSV под вставку отдельными листами в Google Таблицу: `output/sheet_sequence.csv` (цепочка писем), `output/sheet_emails.csv` (готовые письма), `output/sheet_polza_checked.csv` (задача 4, с русскими заголовками и колонкой «Что не сошлось» на видном месте). Источники правды — `email_sequence.md` и сами скрипты; выгрузка генерируется, руками её не правят.

## Запуск

Нужен локальный Ollama с моделью `gpt-oss:20b` (`ollama pull gpt-oss:20b`).
Адрес сервера берётся из переменной окружения `OLLAMA_URL`, по умолчанию
`http://localhost:11434/api/chat`.

**Воспроизвести базу целиком** (все домены уже зафиксированы в
`known_domains.py`, поисковик не задействован — то есть капча, остановившая
первый прогон, здесь не помеха):

```bash
pip install -r requirements.txt
python pass2.py            # сбор по известным доменам: email, имя, персонализация
python finalize.py         # сборка чистого output/leads_final.csv
python build_emails.py     # сборка готовых писем: output/emails_ready.csv
python export_for_sheets.py # выгрузка листов для Google Таблицы
```

**Добавить в базу новые компании** — дописать названия в `companies_seed.py` и
запустить `python collect_leads.py`: он ищет сайты через DuckDuckGo. Именно на
этом шаге исходный прогон и упёрся в капчу после ~10 компаний, поэтому найденные
домены и зафиксированы в `known_domains.py` — повторно искать их не нужно.

⚠️ Скрипты перезаписывают файлы в `output/`, включая уже сданные. Прогон долгий
(сайты + LLM на каждую компанию) и зависит от доступности Ollama и внешних
сайтов — перед повторным запуском скопируйте `output/` в сторону, если нужно
сохранить сданную версию для сравнения.

Итог — **`output/leads_final.csv`**: 59 компаний, колонки `Название, Сайт, Имя, Email, Персонализация, Источник персонализации` (последняя — источник факта, чтобы проверить, что персонализация не выдумана). Шапка на русском намеренно: файл заливается в Google Таблицу как есть, а ТЗ требует по задаче 1 колонки "название, сайт, имя и email" и по задаче 2 столбец "Персонализация". Промежуточный `output/leads.csv` остаётся на латинице — он машинный.

Заполненность: **51 строка с email, 57 с персонализацией, 8 с именем контакта.** Пропуски не забыты, а оставлены пустыми осознанно — по каждому есть причина:

- **email у 51 из 59** — на сайтах остальных почты нет вообще, а угадывать адрес по шаблону `info@домен` нельзя: письмо уйдёт в никуда и испортит репутацию домена отправителя.
- **имя у 8 из 59** — ищется на страницах "Команда"/"Контакты", и у большинства российских агентств там просто нет конкретных людей, только `info@` и телефон. Модели запрещено гадать; в письме вместо имени идёт "Здравствуйте!".
- **персонализация у 57 из 59** — две компании без неё: у одной на сайте нет ни одного конкретного факта, у другой сайт оказался незаполненным демо-шаблоном (см. ниже).

Одна строка ("Лига трафика") в базу не попала: поиск отдавал только группу ВКонтакте, своего сайта у компании нет, а группа соцсети сайтом не считается.

## Технические решения и грабли по пути

- **Кодировка.** Часть сайтов (например, лендинги на Tilda) объявляют `charset=UTF-8` в заголовке и в `<meta>`, но реальный кириллический текст залит с ошибкой перекодировки — классический мохибейк, который обычные детекторы кодировки не ловят, потому что байты формально валидны как UTF-8. Починила через `ftfy.fix_text()` — библиотеку, которая умеет распознавать именно такой паттерн двойной перекодировки.
- **Ложные email.** Регулярка на email иногда ловит не почту, а версии JS-библиотек в тегах `<script>` (вида `player@1.8.0.js`). Добавила фильтр: отсекаю по расширению файла и по доменам, целиком состоящим из цифр.
- **Сеть.** DuckDuckGo/сайты компаний периодически рвут соединение или отвечают долго — добавила retry с backoff на каждый HTTP-запрос, иначе прогон 50+ компаний падает на первой же случайной заминке.
- **Качество персонализации зависит от того, что реально есть на сайте.** Если на главной только список услуг без конкретики — персонализация выйдет более общей (LLM честно суммирует то, что есть, не выдумывает недостающее). Для части компаний, где сайт пуст на факты, персонализация помечена как "недостаточно данных" — намеренно, а не баг.
- **Незаполненный демо-шаблон опаснее пустого сайта.** Главная одной компании отдаёт демо-рыбу WordPress-темы на английском, вместе с плейсхолдером `Display a site wide notice to your visitors here`. Модель добросовестно пересказала её — и в базу уехал продукт, которого у компании не существует. Запрет "не выдумывай" тут бессилен: с точки зрения модели она ничего и не выдумала, дефектен сам источник. Чинится только на входе: `looks_like_template()` отсекает такие страницы по подписям шаблона и по признаку "российский домен без единой кириллической буквы", и персонализация по ним не строится. Проверено на всех 35 `.ru`-сайтах базы — ложных срабатываний нет.
- **Имя контакта нельзя брать откуда попало.** Первая версия вытащила в контакты владельца арт-галереи, для которой агентство делало открытки, — то есть чужого человека из раздела работ, да ещё в родительном падеже. Промпт теперь прямо запрещает брать людей из портфолио и отзывов, а `normalize_contact_name()` страхует его правилом: если имя дословно встречается в тексте персонализации, оно взято из рассказа о клиентах. Заодно ФИО сокращается до имени — "Привет, Новицкий Сергей Владимирович!" в холодном письме звучит как повестка.
- **Лимит длины считается по собранному письму, а не по шаблону.** Шаблон письма 1 укладывается в 87 слов при лимите ТЗ 120, но персонализация добавляет ещё 30-50 — и в готовом письме лимит превышался. `build_emails.py` считает бюджет слов по каждой строке и укорачивает персонализацию (сначала по целым предложениям, в крайнем случае по словам): урезается она, а не выверенный текст письма.

## Задача 4 — персонализация базы клиента

В базе от клиента 15 компаний из другой ниши (станки и металлообработка) и прямая
подсказка в задании: «будь начеку, вдруг мы что-то перепутали». Перепутали:
замечания нашлись у 8 строк из 15. Полный разбор с доказательствами — в
[task4_analysis.md](task4_analysis.md).

Коротко, что не так с базой: у пяти компаний в колонке сайта стоит чужой домен
(строки 6 и 7 просто обменялись доменами, у остальных сдвиг), один домен указан
сразу у двух компаний, у части строк домен почты не совпадает с доменом сайта,
две компании вообще не из ниши базы, а на одном из сайтов главная страница
нашпигована посторонними SEO-ключами, которые нельзя пускать в персонализацию.

**`check_and_personalize.py`** исходит из того, что колонке с сайтом доверять
нельзя. По каждой строке он:

1. Открывает сайт из базы, перебирая варианты адреса (https, www, http) —
   без этого два живых сайта из базы выглядели бы мёртвыми.
2. Определяет, кому сайт реально принадлежит: локальная LLM выносит вердикт по
   заголовку и тексту страницы, гадать ей запрещено.
3. Проверяет механику: домен почты против домена сайта **и против реально
   найденного сайта**, бесплатные ящики, повторяющиеся домены по всей базе.
   Второе важнее первого: если у строки подменены и сайт, и почта
   согласованно, сверка только с базой промолчит — именно так у Tesid
   письмо про китайские станки ушло бы российскому «Юнимашу».
4. Если сайт из базы чужой или мёртвый — ищет настоящий сайт компании и
   перебирает кандидатов до первого живого (`polza_known_sites.py` — проверенные
   вручную адреса как запасной вариант, когда поисковик отдаёт капчу или
   мёртвую ссылку).
5. Если настоящий сайт найти не удалось, компания остаётся **без
   персонализации**. Строить её по чужому сайту нельзя — иначе Rogen
   Technologies получит письмо про продукцию JAT.
6. Определяет отрасль и попадание в нишу базы. Компании вне ниши не удаляются,
   а помечаются: решение об исключении из рассылки за клиентом.
7. Пишет персонализацию по реально найденному сайту и на его языке: русский для
   российских компаний, английский для китайских экспортёров.

```bash
python check_and_personalize.py
```

Итог — **`output/polza_checked.csv`**: 15 из 15 компаний с персонализацией,
каждая построена по сайту настоящего владельца. Кроме персонализации в таблице
есть колонки проверки — `site_status`, `site_owner`, `verdict`, `site_used`,
`site_source`, `industry`, `niche`, `issues`, — то есть видно не только результат,
но и что именно в базе не сошлось и на каком основании.

## Тесты

```bash
python test_pipeline.py          # без зависимостей
python -m pytest test_pipeline.py -q   # если стоит pytest
```

39 тестов на функции, которые работают без сети и без LLM: выбор email,
перебор вариантов адреса, очистка текста перед подачей в модель, нормализация
имени контакта, детект демо-шаблона, поиск страницы команды и подгонка письма
под лимит слов.

Покрытие выбрано не для галочки — каждый тест воспроизводит баг, который
реально был. Выбор email по алфавиту клал в базу `buh@` (бухгалтерию) вместо
продаж; сравнение доменов подстрокой на паре `ony.ru` / `anthony@partner.com`
брало чужой адрес, а домен без точки ронял скрипт с `IndexError`; в колонку
имени попадал человек из чужого портфолио; письмо выбивалось за лимит ТЗ.
Всё это ловится за секунды и без единого сетевого запроса — а найдено было
дорогой ценой, на живых прогонах.

Python, httpx (HTTP-запросы), BeautifulSoup (парсинг HTML), ftfy (починка кодировки), локальная LLM через Ollama (та же связка, что в smart-intake-automation).
